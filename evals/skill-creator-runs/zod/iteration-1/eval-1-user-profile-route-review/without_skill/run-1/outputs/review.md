# Code Review: `user-profile-schema.ts` (profile-update route)

Файл: `.claude/skills/zod-workspace/fixtures/user-profile-schema.ts`

Загальний висновок: маршрут `PUT /me/profile` виглядає робочим на перший погляд,
але `GET /me/profile` містить критичний баг у WHERE-умові, а обробка вхідних
даних (Zod-валідація, помилки) недостатньо надійна для production. Нижче —
знахідки за спаданням критичності, кожна з поясненням "чому це важливо" і
пропозицією виправлення.

---

## Critical

### 1. `GET /me/profile` — WHERE-умова порівнює JS-об'єкт колонки зі значенням, а не будує SQL-умову

**Рядок 53:**
```ts
const [row] = await db.select().from(userProfiles).where((t) => t.userId === req.userId);
```

**Чому це критично:** `t.userId` у callback'у Drizzle — це об'єкт-дескриптор
колонки (`Column`), а не значення рядка. `t.userId === req.userId` — це
звичайне строге порівняння JS-об'єкта зі строкою, яке виконується один раз під
час побудови запиту і завжди дає `false`. Це не будує SQL-предикат `WHERE
user_id = $1`, а натомість передає в `.where()` буквальний булевий `false`
(або взагалі невалідний тип, залежно від версії Drizzle — можливий runtime-throw
на етапі побудови запиту). У найкращому разі маршрут завжди повертатиме "не
знайдено" для будь-якого користувача; у гіршому — впаде з помилкою типів, або,
що найнебезпечніше, поверне **перший-ліпший рядок таблиці** (якщо предикат
проігнорується як truthy), тобто профіль чужого користувача.

**Виправлення:** використати оператор Drizzle `eq()`:
```ts
import { eq } from 'drizzle-orm';

const [row] = await db
  .select()
  .from(userProfiles)
  .where(eq(userProfiles.userId, req.userId))
  .limit(1);
```

### 2. `UserProfileSchema.parse()` кидає виняток, який ніде не обробляється як 400

**Рядок 24:**
```ts
const input = UserProfileSchema.parse(req.body) as UserProfileInput;
```

**Чому це важливо:** `.parse()` кидає `ZodError` при будь-якому невалідному
тілі запиту (наприклад, `displayName` довший за 80 символів, або `avatarUrl`
не є валідним URL). У цьому файлі немає ні `try/catch`, ні
`schema`-опції на рівні Fastify-роута, ні згадки про глобальний
error-handler, що мапить `ZodError` → 400. Якщо такого handler'а немає десь
вище по коду — цілком звичайна помилка валідації клієнта (400 Bad Request)
перетвориться на 500 Internal Server Error, зіпсує моніторинг/алерти і дасть
клієнту незрозумілу відповідь.

**Виправлення:** або явно обробити помилку в хендлері, або підключити
Zod type provider / `setErrorHandler`, що мапить `ZodError` на 400 з деталями
полів:
```ts
const parsed = UserProfileSchema.safeParse(req.body);
if (!parsed.success) {
  reply.status(400);
  return { error: 'Invalid request', issues: parsed.error.flatten() };
}
const input = parsed.data;
```

### 3. `metadata: z.any()` — фактично відсутність валідації

**Рядок 10:**
```ts
metadata: z.any(),
```

**Чому це важливо:** `z.any()` пропускає буквально будь-яке значення —
об'єкт довільної глибини/розміру, масив, рядок, число, `null`. Це зводить
нанівець сенс мати Zod-схему саме для цього поля: немає обмеження розміру
(ризик роздування jsonb-колонки / DoS через величезний payload), немає
обмеження форми (downstream-код, що читає `metadata`, не може покладатися на
жодну структуру), і немає захисту від "сміттєвих" ключів на кшталт
`__proto__`/`constructor` у вкладених об'єктах, якщо `metadata` десь далі
буде змерджено в інший об'єкт без обережності.

**Виправлення:** визначити явну (нехай навіть часткову) форму або хоча б
розумні межі:
```ts
metadata: z.record(z.string(), z.unknown()).refine(
  (obj) => JSON.stringify(obj).length <= 10_000,
  { message: 'metadata payload too large' },
),
```

### 4. Ручний тип `UserProfileInput` дублює Zod-схему і розходиться з нею — `as`-каст ховає це розходження

**Рядки 6–20:**
```ts
const UserProfileSchema = z.object({ /* ... */ metadata: z.any(), /* ... */ });

type UserProfileInput = {
  /* ... */
  metadata: unknown;
  /* ... */
};
```

**Чому це важливо:** сенс Zod — мати єдине джерело правди для типу й валідації
(`z.infer<typeof Schema>`). Тут тип виписаний вручну і вже розходиться зі
схемою: `z.any()` дає TS-тип `any`, а ручний тип оголошує `unknown`. Оскільки
результат `.parse()` одразу кастується через `as UserProfileInput` (рядок
24), TypeScript **не перевіряє** відповідність — каст мовчки "заглушує" будь-
яку розбіжність. Якщо хтось пізніше додасть/перейменує поле в схемі й забуде
оновити цей тип (або навпаки), компілятор цього не впіймає, і баг спливе лише
в runtime.

**Виправлення:** прибрати ручний тип і каст, вивести тип зі схеми:
```ts
type UserProfileInput = z.infer<typeof UserProfileSchema>;
// ...
const input = UserProfileSchema.parse(req.body); // без `as`
```

## Important

### 5. `avatarUrl: z.string().url()` приймає будь-яку схему URL, не лише http(s)

**Рядок 9:**
```ts
avatarUrl: z.string().url().optional(),
```

**Чому це важливо:** `.url()` у Zod валідує за WHATWG URL-парсером, який
приймає `javascript:`, `data:`, `file:`, `ftp:` тощо — не лише `http(s):`.
Якщо `avatarUrl` пізніше рендериться як `<img src>` без додаткової перевірки
на фронтенді, або використовується сервером для якогось fetch/proxy-запиту,
це відкриває шлях до XSS (`javascript:`-псевдопротокол у деяких контекстах)
або SSRF/локального доступу до файлів.

**Виправлення:**
```ts
avatarUrl: z.string().url().refine(
  (url) => /^https?:\/\//i.test(url),
  { message: 'avatarUrl must be http(s)' },
).max(2048).optional(),
```

### 6. Немає обмеження довжини `avatarUrl`

Пов'язано з п.5: без `.max(...)` можна передати мега-довгий `data:`-URL (сотні
кілобайт base64), що роздує рядок у БД і навантажує serialization на кожному
GET. Додати `.max(2048)` (або іншу розумну межу) поруч з перевіркою схеми.

### 7. `timezone` не перевіряється на валідність IANA-таймзони

**Рядок 11:**
```ts
timezone: z.string().default('UTC'),
```

**Чому це важливо:** будь-який рядок ("banana", "UTC+25") пройде валідацію.
Якщо десь далі в коді `timezone` передається в `Intl.DateTimeFormat` або
date-library, невалідне значення кине runtime-виняток у зовсім іншому місці
коду, далеко від точки, де його легко було б відловити.

**Виправлення:**
```ts
const VALID_TIMEZONES = new Set(Intl.supportedValuesOf('timeZone'));
timezone: z.string().refine((tz) => VALID_TIMEZONES.has(tz), {
  message: 'Invalid IANA timezone',
}).default('UTC'),
```

### 8. Немає явної перевірки автентифікації (`req.userId`) перед записом у БД

**Рядки 29, 53:** обидва хендлери напряму використовують `req.userId` без
перевірки, що воно взагалі існує. Якщо auth-плагін, що встановлює
`req.userId`, підключений не на всіх шляхах (або підключений з помилкою),
`insert` піде з `userId: undefined` — залежно від типу колонки це або
впаде на NOT NULL/FK constraint (500 замість 401), або, гірше, якщо колонка
nullable — створить "анонімний" профіль. Це важливо перевірити явно в самому
хендлері, а не покладатися виключно на зовнішній middleware, який не видно з
цього файлу.

**Виправлення:**
```ts
if (!req.userId) {
  reply.status(401);
  return { error: 'Unauthorized' };
}
```

### 9. Дублювання полів між `insert().values()` і `onConflictDoUpdate().set()`

**Рядки 28–34 і 39–44** — ідентичний набір полів виписаний двічі. Це джерело
розходжень: додаси нове поле в один блок і забудеш у другий — і upsert почне
поводитись по-різному для create/update.

**Виправлення:** винести спільний об'єкт:
```ts
const profileData = {
  displayName: input.displayName,
  bio: input.bio ?? null,
  avatarUrl: input.avatarUrl ?? null,
  metadata: input.metadata,
  timezone: input.timezone,
};

const [row] = await db
  .insert(userProfiles)
  .values({ userId: req.userId, ...profileData })
  .onConflictDoUpdate({ target: userProfiles.userId, set: profileData })
  .returning();
```

### 10. Відсутня response-схема — клієнту повертається сирий рядок з БД

**Рядки 48–49, 58:** `return row` віддає весь рядок таблиці як є. Якщо в
`userProfiles` є службові/внутрішні колонки (наприклад, службові прапорці,
internal notes, майбутні поля, додані міграцією), вони автоматично потраплять
у відповідь API без явного рішення про це. Варто явно змапити відповідь на
публічний DTO (це також узгоджується з конвенцією проєкту "wire contracts —
snake_case, мапінг на межі роута").

## Minor / nice-to-have

- **Рядок 53:** додати `.limit(1)` до `SELECT` — семантично очікується рівно
  один рядок (userId унікальний), явний `limit` документує це і трохи
  економить на I/O у разі майбутньої відсутності унікального індексу.
- **Рядок 48:** `reply.status(200)` для upsert, який може бути першим
  створенням профілю — з точки зору REST це міг би бути `201 Created` для
  create-гілки й `200` для update-гілки; не критично для upsert-семантики,
  але варто узгодити з рештою API проєкту.
- Немає `try/catch`/явної стратегії обробки помилок БД (наприклад, унікальний
  constraint, обрив з'єднання) — наразі вони так само провалюються в
  дефолтний Fastify error-handler без диференціації від помилок валідації
  (див. п.2). Варто мати єдину, свідому стратегію для обох класів помилок.
- Немає перевірки, що `req.body` взагалі є об'єктом до виклику `.parse()` —
  не критично (Zod сам це відхилить), просто зауваження, що поведінка на
  порожньому/невалідному тілі повністю залежить від виправлення п.2.
