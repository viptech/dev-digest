# Code Review: `profileRoutes` (profile-update route)

Файл: `user-profile-schema.ts` (Fastify handler, upsert профілю користувача)

Огляд нижче впорядкований за критичністю: спочатку блокери (мають бути виправлені
до відкриття PR), потім важливі проблеми, потім дрібніші зауваження та стиль.

---

## 🔴 Critical

### 1. `GET /me/profile` — `.where()` ніколи не відфільтрує правильний рядок
**Рядок 53:**
```ts
const [row] = await db.select().from(userProfiles).where((t) => t.userId === req.userId);
```
Це виглядає як звичайний JS-колбек, що порівнює `t.userId === req.userId`. У Drizzle
`.where()` очікує SQL-вираз, побудований через оператори (`eq`, `and`, ...), а не
булевий результат JS-порівняння колонки (об'єкта-дескриптора) зі значенням. Тут
`t.userId` — це об'єкт-колонка, а не рядкове значення, тож `t.userId === req.userId`
завжди `false` (порівняння об'єкта з рядком за посиланням). У найкращому разі це не
скомпілюється (TS помітить, що callback повертає `boolean`, а очікується SQL-умова);
у гіршому — якщо типи десь послаблені (`any`), запит піде без реального фільтра і
поверне довільний/перший рядок таблиці **чужого** користувача — витік чужого профілю.

**Чому це важливо:** ендпойнт призначений повертати профіль *поточного* користувача.
Зламаний фільтр — це або миттєвий runtime-crash, або (гірший сценарій) IDOR: користувач
А бачить дані користувача Б.

**Фікс:**
```ts
import { eq } from 'drizzle-orm';
...
const [row] = await db
  .select()
  .from(userProfiles)
  .where(eq(userProfiles.userId, req.userId));
```

### 2. `req.userId` використовується без перевірки автентифікації
**Рядки 29, 37, 53.**

Ніде в хендлері не видно перевірки, що `req.userId` взагалі існує (автентифікований
запит) і має правильний тип. Якщо `req.userId` може бути `undefined` (немає
auth-preHandler на цьому роуті, або токен не валідний), то:
- в `PUT` — `insert(...).values({ userId: undefined, ... })` або вставить `NULL`,
  або впаде з помилкою NOT NULL/FK constraint, залежно від схеми;
- в `GET` — після фіксу з п.1, `eq(userProfiles.userId, undefined)` поверне порожню
  вибірку (не крах, але прихована діра — незалогінений клієнт отримує 404 замість 401).

**Чому це важливо:** роут, що модифікує/читає персональні дані, повинен явно
залежати від автентифікації, а не покладатися на те, що `req.userId` "десь"
підставляється іншим middleware. Якщо це справді робиться в глобальному хуку —
варто хоча б додати `preHandler`/guard саме на цьому плагіні та явно типізувати
`req.userId` через `declare module 'fastify' { interface FastifyRequest { userId: string } }`,
щоб TS не пропускав `undefined`.

**Фікс:**
```ts
app.put('/me/profile', { preHandler: app.authenticate }, async (req, reply) => {
  if (!req.userId) {
    reply.status(401);
    return { error: 'Unauthorized' };
  }
  ...
```
(або еквівалент наявного auth-механізму проєкту — головне, щоб це було видно в
самому файлі роута, а не малося на увазі).

## 🟠 High

### 3. `metadata: z.any()` — без жодної валідації структури чи розміру
**Рядок 10, використання — рядки 33, 42.**

`z.any()` пропускає що завгодно: рядок, число, масив на 50 МБ, глибоко вкладений
об'єкт, `null`, навіть функцію (яка потім не серіалізується в JSON і призведе до
дивної поведінки). Це поле йде прямо в БД (ймовірно `jsonb`-колонка) без обмежень.

**Чому це важливо:**
- DoS-вектор: клієнт може надіслати величезний або патологічно вкладений JSON,
  що роздує рядок у БД чи вантажить сервер серіалізацією/десеріалізацією.
- Немає жодної гарантії форми даних для коду, який пізніше читає `metadata` —
  будь-яке інше місце в кодовій базі, що очікує `metadata.someField`, впаде на
  `undefined`/невідповідному типі.
- Це єдине поле в схемі без **жодної** межі, тоді як усі інші (`displayName`,
  `bio`) свідомо обмежені `.max(...)`.

**Фікс:** мінімум — обмежити тип і розмір:
```ts
metadata: z.record(z.string(), z.unknown()).refine(
  (v) => JSON.stringify(v).length <= 10_000,
  { message: 'metadata payload too large' },
).optional().default({}),
```
Краще — визначити конкретну форму `metadata`, якщо вона взагалі передбачувана
(навіть `z.record(z.string(), z.union([z.string(), z.number(), z.boolean()]))`
значно безпечніше за `z.any()`).

### 4. `UserProfileSchema.parse(req.body)` без обробки помилки валідації
**Рядок 24.**

`.parse()` кидає `ZodError`, якщо тіло не пройшло валідацію. У хендлері немає
`try/catch`, і незрозуміло, чи в проєкті є глобальний `setErrorHandler`, який
перетворює `ZodError` на охайну `400`-відповідь. Якщо такого глобального
обробника немає (а в файлі це ніяк не перевірити і не задокументовано), клієнт
при невалідному тілі отримає `500 Internal Server Error` замість `400 Bad Request`,
а в логах — стек-трейс Zod, що потенційно віддає деталі внутрішньої схеми назовні
(залежно від конфігурації error handler'а).

**Чому це важливо:** невалідний, але цілком очікуваний user input (порожній
`displayName`, задовгий `bio`, кривий `avatarUrl`) — це нормальний кейс роботи
API, не виняткова ситуація на рівні 500-ки. З точки зору клієнта/фронтенду це
критично для UX форми редагування профілю.

**Фікс:** або явний `try/catch` з мапінгом на `400`:
```ts
const parsed = UserProfileSchema.safeParse(req.body);
if (!parsed.success) {
  reply.status(400);
  return { error: 'Invalid profile payload', issues: parsed.error.issues };
}
const input = parsed.data;
```
або (якщо в проєкті вже є `fastify-type-provider-zod`/глобальний error handler
для `ZodError`) — хоча б залишити коментар у коді, що це навмисно делеговано
туди, щоб рецензент/наступний автор не гадав.

### 5. Ручний тип `UserProfileInput` дублює `UserProfileSchema` і застосовується через непрозорий `as`
**Рядки 14–20, 24.**

```ts
const input = UserProfileSchema.parse(req.body) as UserProfileInput;
```

`.parse()` вже повертає точно типізоване значення (`z.infer<typeof UserProfileSchema>`).
Кастомний `UserProfileInput`, написаний вручну, — це друге джерело правди, яке
може розсинхронізуватися зі схемою (наприклад, хтось додасть нове обов'язкове
поле в `UserProfileSchema` і забуде оновити `UserProfileInput` — TS не підкаже,
бо `as` — це силове приведення, не перевірка сумісності).

**Чому це важливо:** сенс Zod у зв'язці "одне джерело правди для рантайм-валідації
і статичних типів". Ручний дубльований тип + `as`-каст усуває саме цю гарантію і
відкриває шлях до тихого неспівпадіння типів у майбутньому.

**Фікс:**
```ts
type UserProfileInput = z.infer<typeof UserProfileSchema>;
...
const input = UserProfileSchema.parse(req.body); // тип виводиться автоматично
```
Прибрати ручний `type UserProfileInput = { ... }` повністю.

### 6. `avatarUrl: z.string().url()` не обмежує протокол
**Рядок 9.**

`.url()` у Zod валідує лише те, що рядок парситься як коректний URL (через
`new URL()`), але не обмежує схему. Значення на кшталт `javascript:alert(1)`,
`data:text/html;base64,...` або `file:///etc/passwd` пройдуть валідацію, якщо
формально валідні як URL.

**Чому це важливо:** якщо `avatarUrl` потім рендериться як `<img src>` чи
`<a href>` на фронтенді без додаткової санітизації — це XSS-вектор
(`javascript:`) або спроба локального доступу до файлів (`file:`) в певних
контекстах рендеру. Навіть якщо сьогодні фронтенд ставить санітизацію,
бекенд-схема — правильне місце зафіксувати інваріант "лише http/https".

**Фікс:**
```ts
avatarUrl: z.string().url().refine(
  (u) => /^https?:\/\//i.test(u),
  { message: 'avatarUrl must use http or https' },
).optional(),
```

## 🟡 Medium

### 7. Відповідь віддає сирий рядок з БД без явної DTO-мапи (і без snake_case-контракту)
**Рядки 46–49, 58.**

`return row;` віддає весь результат `.returning()` / `.select()` як є — усі
колонки таблиці `userProfiles`, включно з тими, що можуть з'явитися пізніше
(службові поля, внутрішні прапорці, timestamps тощо), у "сирому" camelCase
вигляді напряму на дріт.

**Чому це важливо:** для цього проєкту явно зафіксована конвенція — wire-контракти
`snake_case` (`head_sha`, `files_count`), а маппінг camelCase → snake_case робиться
явно на межі роута (`server/src/vendor/shared/contracts/`). Тут такого мапінгу
немає взагалі — камелкейс з Drizzle йде прямо в JSON-відповідь. Окрім
невідповідності контракту, це ще й "case leaking" — будь-яка нова колонка в
таблиці автоматично і без рев'ю потрапляє у публічний API.

**Фікс:** явно сформувати відповідь:
```ts
return {
  user_id: row.userId,
  display_name: row.displayName,
  bio: row.bio,
  avatar_url: row.avatarUrl,
  metadata: row.metadata,
  timezone: row.timezone,
};
```
(або через спільний контракт-тип/мапер, якщо такий вже є в
`server/src/vendor/shared/contracts/`).

### 8. `displayName` не тримується (`.trim()`) — рядок з самих пробілів пройде `.min(1)`
**Рядок 7.**

`z.string().min(1).max(80)` перевіряє довжину рядка як є. `"   "` (три пробіли)
має довжину 3 і успішно пройде валідацію, залишивши користувача з візуально
порожнім іменем.

**Фікс:**
```ts
displayName: z.string().trim().min(1).max(80),
```
Аналогічно варто розглянути `.trim()` для `bio`.

### 9. `timezone` не перевіряється як реальний IANA-ідентифікатор
**Рядок 11.**

`z.string().default('UTC')` приймає будь-який рядок — `"asdf"`, `"Mars/Phobos"`
тощо. Пізніше, якщо цей рядок передається в `Intl.DateTimeFormat(..., { timeZone })`
чи подібне, некоректне значення призведе до `RangeError` у зовсім іншому місці
кодової бази, далеко від точки, де дані потрапили в систему.

**Фікс:** мінімально — валідувати через сам рантайм:
```ts
timezone: z.string().default('UTC').refine(
  (tz) => {
    try { Intl.DateTimeFormat(undefined, { timeZone: tz }); return true; }
    catch { return false; }
  },
  { message: 'Invalid IANA timezone' },
),
```

### 10. Немає обробки помилок БД (унікальні/FK-констрейни, збій з'єднання)
**Рядки 26–46.**

`onConflictDoUpdate({ target: userProfiles.userId, ... })` мовчазно передбачає,
що на `userProfiles.userId` є унікальний індекс/PK у схемі — файл цього не
підтверджує (схема тут не наведена). Якщо такого констрейна немає, `onConflictDoUpdate`
або впаде з помилкою Postgres під час рантайму, або (залежно від версії
Drizzle/Postgres) поведінка upsert буде іншою, ніж очікується.

**Чому це важливо:** варто явно перевірити (і в PR-описі зазначити), що
`userProfiles.userId` дійсно унікальний/primary key в `db/schema.ts` — без
цього весь upsert-механізм ненадійний, і крах стається лише в рантаймі під
навантаженням, не на етапі рев'ю.

**Фікс:** якщо це вже гарантовано схемою — додати короткий коментар над
викликом (`// userId is unique, see db/schema.ts`), щоб було видно намір;
якщо ні — додати міграцію з унікальним індексом до відкриття PR.

## 🟢 Low / Style

### 11. `z.object` без `.strict()` — зайві поля в тілі тихо відкидаються
**Рядок 6.**

За замовчуванням Zod у режимі "strip" тихо видаляє невідомі ключі з `req.body`.
Це не помилка, але для API endpoint часто зручніше явно відхиляти запити з
неочікуваними полями (`.strict()`), щоб клієнтські баги (typo в назві поля,
застаріла версія фронтенду) були помітні одразу як `400`, а не мовчки
ігнорувалися.

### 12. `reply.status(200)` на upsert — варто розрізняти "створено" / "оновлено"
**Рядок 48.**

Семантично `PUT`-upsert може повертати `201 Created` при першому створенні
профілю і `200 OK` при оновленні. Не критично (`200` для `PUT` цілком прийнятний
за HTTP-семантикою), але якщо клієнту важливо розрізняти ці випадки — Drizzle
`.returning()` не каже, чи стався insert чи update; варто або прийняти `200`
завжди свідомо, або відстежувати case окремо.
