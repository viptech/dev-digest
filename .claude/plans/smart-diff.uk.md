# План розробки — Smart Diff

## Контекст

Сьогодні `GET /pulls/:id` повертає `files: PrFile[]` (`path`/`additions`/
`deletions`/`patch`) у тому порядку, в якому їх зберігає GitHub/`t.prFiles`,
а клієнтський `DiffTab` (`client/src/app/repos/[repoId]/pulls/[number]/_components/DiffTab/DiffTab.tsx`)
рендерить їх напряму через `<DiffViewer files={files} .../>` без жодного
групування. Рев'юєру, який відкриває великий PR, доводиться прокручувати повз
`package-lock.json` і згенерований boilerplate, щоб знайти той один файл, що
дійсно має значення, а після запуску рев'ю немає способу перейти від finding
одразу до його рядка — findings з'являються лише в окремому UI рев'ю, а не
inline у diff.

Smart Diff групує вже імпортовані файли PR за **роллю ризику** — `core`
(бізнес-логіка), `wiring` (конфіг/index/зв'язки), `boilerplate` (lock-файли,
`dist/`, снепшоти) — так щоб рев'юєр бачив спершу core-логіку, а boilerplate
за замовчуванням був згорнутий. Це **не** нова LLM-фіча: вона детерміновано
комбінує два джерела, які вже існують у базі даних —

1. `t.prFiles` (`path`, `additions`, `deletions`, `patch`) — вже персистяться
   через `GET /pulls/:id` (`server/src/modules/pulls/routes.ts:234-245` на
   шляху GitHub-рефрешу, `routes.ts:273` на шляху офлайн-фолбеку).
2. Findings **останнього** рев'ю (`file`, `start_line`/`end_line`,
   `severity`) — вже персистяться в `t.reviews`/`t.findings` і вже
   запитуються саме таким чином (останнє на PR через `kind: 'review'` +
   `orderBy(desc(createdAt))`, first-seen-wins) у
   `server/src/modules/pulls/routes.ts:130-139`.

Контракт відповіді вже існує, лише не підключений: `SmartDiff`/`SmartDiffGroup`/
`SmartDiffFile`/`ProposedSplit` у
`server/src/vendor/shared/contracts/brief.ts:93-126` (дзеркально в
`client/src/vendor/shared/contracts/brief.ts`), підтверджено ідентичними між
серверною та клієнтською копіями цієї сесії. Класифікація запускається
одразу, щойно файли доступні (одразу після імпорту PR — "не викликає
модель"); findings приєднуються, коли вони є. **Тут немає непідключеного
scaffolding, який слід перевіряти**, як було з таблицею `pr_intent` в Intent
Layer — у `SmartDiff` сьогодні нуль викликів (підтверджено grep'ом), його
треба будувати з нуля, попередньо визначена лише форма.

## Модулі, яких це стосується

- **server** — новий детермінований класифікатор файлів (чиста функція, без
  I/O), новий роут `GET /pulls/:id/smart-diff`, і (невеликі) доповнення
  доступу до даних для читання findings останнього рев'ю по PR.
- **shared contracts** (`server/src/vendor/shared` + вручну продубльована
  копія `client/src/vendor/shared`) — `SmartDiff` вже існує з обох боків;
  цей план не потребує *нових* полів там, але дивись рішення щодо
  `pseudocode_summary` в розділі Constraints.
- **client** — новий `SmartDiffViewer` (або `SmartDiffTab`/перемикач режиму
  на існуючому `DiffTab`), що групує файли за роллю, тримає `boilerplate`
  згорнутим, показує бейдж "N findings" на файл і скролить diff до рядка
  клікнутого finding.
- **reviewer-core** — поза межами. Smart Diff ніколи не торкається промпту
  рев'ю чи `assemblePrompt`; вона лише читає *результати* рев'ю
  (`findings`), ніколи нічого не передає назад у вхід рев'ю.
- **e2e** — поза межами згідно `TESTING.md` (лише детерміновані e2e; Smart
  Diff не має LLM-кроку, який би потребував hermetic-мокінгу понад те, що
  вже надають фікстури diff/review, але smoke-перевірку можна додати
  пізніше — цим планом не вимагається).

## Обмеження

- **Жодного нового виклику LLM ніде в цій фічі.** Це основний критерій
  прийнятності ("У логах перегляду Smart Diff немає нового виклику
  моделі"). Класифікатор ніколи не повинен імпортувати `resolveFeatureModel`
  (`server/src/modules/settings/feature-models.ts`) чи викликати
  `container.llm(...)` (`server/src/platform/container.ts:163`) — єдину
  точку доступу до моделі в цьому репо. Конкретно перевірюване: `grep -n
  "container.llm(\|resolveFeatureModel(" server/src/modules/smart-diff/`
  (чи де б класифікатор не опинився) має нічого не повертати.
- **`SmartDiffFile.pseudocode_summary`** (`brief.ts:99`, `z.string().nullish()`)
  явно проєктувалося з думкою про майбутній крок LLM-сумаризації. Класифікатор
  цього плану **не** заповнює його — кожен `SmartDiffFile` має ставити його
  в `null`, ніколи не вигадувати summary. Явно зазначити це в описі PR
  імплементера, щоб це читалося як свідоме рішення про обсяг, а не як баг чи
  недогляд.
- **Wire-контракти snake_case, серверна та клієнтська копії мають
  синхронізуватися вручну** (кореневий `CLAUDE.md`; той самий інцидент з
  розбіжністю полів `Intent`, зафіксований у кореневому `INSIGHTS.md`,
  2026-07-31, є причиною, чому це важливо). `SmartDiff` вже існує ідентично
  з обох боків — якщо форма роуту/відповіді цього плану потребуватиме *будь-якого*
  коригування контракту (наприклад, виявиться, що `finding_lines` потребує
  `severity` поряд з номером рядка — дивись Ordered steps нижче), редагувати
  одразу і `server/src/vendor/shared/contracts/brief.ts`, і
  `client/src/vendor/shared/contracts/brief.ts`.
- **Форма модуля** (`server/CLAUDE.md`): `modules/<name>/` =
  `routes.ts` + `service.ts` + `repository.ts` (розбивається на
  `repository/<entity>.repo.ts`, коли доступ до даних розростається). Сам
  модуль `pulls` є винятком — у нього немає `repository.ts`, він читає
  `container.db` + `t.prFiles`/`t.pullRequests` напряму
  (`server/src/modules/pulls/routes.ts`) — підтверджено повторним читанням
  файлу цієї сесії; **не копіювати цей виняток** для нового коду, для роуту
  Smart Diff слідувати стандартній трифайловій формі, де б він не жив.
- **Найменування БД**: snake_case SQL / camelCase Drizzle, згідно кореневого
  `CLAUDE.md`. Smart Diff **не потребує нової таблиці** — вона обчислюється
  при читанні з `t.prFiles` + `t.reviews`/`t.findings`, той самий патерн
  "без FK-денормалізації, дешеві IN-запити + групування в JS", що вже
  використовується для колонок score/findings у списку PR
  (`pulls/routes.ts:123-157`).
- **Міграції**: не застосовується — жодних змін схеми в цьому плані.
- **Grounding-гейт** (`reviewer-core/src/grounding.ts`) і **injection-гард**
  (`reviewer-core/src/prompt.ts`) обидва не зачіпаються цією фічею — Smart
  Diff ніколи не збирає промпт і не продукує finding; вона лише
  повторно відображає findings, які рев'ю вже створило й обґрунтувало.
- **Патерн best-effort join'у, вже встановлений саме для такого типу
  проблеми**: `pulls/routes.ts:222` (`container.reviewRepo.getIntent(pr.id).catch(() => undefined)`)
  — це прецедент, якому слід слідувати: пошук findings для Smart Diff має
  деградувати до порожнього `finding_lines: []` на файл (не валити весь
  запит), коли жодне рев'ю ще не запускалося, відповідно до власної вимоги
  плану "До рев'ю сортування працює без накладок".

## Skills, які використає імплементер

- **`onion-architecture`** — класифікатор є чистою доменною логікою
  (порівняння шляхів/патернів, нуль I/O) і не повинен напряму діставатися
  до адаптерів; шар роуту лишається тонким HTTP↔service транслятором,
  слідуючи тій самій формі `routes.ts`→`service.ts`→`repository.ts`, яку
  документує `server/CLAUDE.md` (а не успадкованому винятку модуля `pulls`).
- **`zod`** — повторне використання наявних схем `SmartDiff`/`SmartDiffGroup`/
  `SmartDiffFile`/`ProposedSplit` (`brief.ts:93-126`); якщо якесь поле
  потребуватиме коригування, слідувати наявним у цьому репо конвенціям
  safe-parse (`feature-models.ts:46`).
- **`fastify-best-practices`** — новий роут `GET /pulls/:id/smart-diff` має
  слідувати наявній у цьому репо конвенції zod-схеми-на-роут
  (`server/src/modules/reviews/routes.ts`, `server/src/modules/pulls/routes.ts`).
- **`drizzle-orm-patterns`** — запит join'у findings (останнє рев'ю на PR,
  `kind: 'review'`, `orderBy(desc(createdAt))`, first-seen-wins, потім
  `inArray(t.findings.reviewId, ...)`) майже точно повторює
  `pulls/routes.ts:130-157`; нової таблиці немає, але методу репозиторію
  потрібна та сама форма IN-запиту.
- **`react-ui-architecture`** / **`react-best-practices`** — рішення, чи є
  `SmartDiffViewer` новою верхньорівневою вкладкою, перемикачем режиму
  всередині наявного `DiffTab`, чи новою фіче-папкою `_components/SmartDiffViewer/`
  (слідуючи патерну `IntentCard`: `SmartDiffViewer.tsx` + `index.ts` +
  `styles.ts` + можливо `constants.ts` для лейблів/кольорів ролей) — і
  підключення поведінки скрол-до-рядка до наявного `@/components/diff-viewer`
  (підкомпоненти `FileCard`/`CodeLine`), а не переписування рендерингу diff з
  нуля.
- `engineering-insights` — не для планувальника викликати, імплементер
  фіксує його по завершенні власної роботи, згідно з протоколом сесій репо.

## Впорядковані кроки

### 1. Класифікатор файлів (чистий, на константах)

- Нова чиста функція, наприклад `classifyFile(path: string): SmartDiffRole`, з
  **усіма порогами й патернами, винесеними в окремий файл констант**
  (явний критерій прийнятності: "Пороги й патерни винесені в константи") —
  наприклад `server/src/modules/smart-diff/classification-rules.ts` (або
  колокований там, де б модуль не опинився), ніколи не inline-регекс-літерали
  в тілі класифікатора.
- Форма правила (детермінована, оцінюється лише за шляхом — `additions`/
  `deletions` ніколи не впливають на роль, лише на відображення):
  - **`boilerplate`** — lock-файли (`package-lock.json`, `pnpm-lock.yaml`,
    `yarn.lock`), білд-вивід (`dist/`, `build/`, `.next/`), снепшоти
    (`__snapshots__/`, `*.snap`) та інші суто згенеровані артефакти. Має бути
    безумовним і найвищим пріоритетом у порядку зіставлення — власний
    критерій прийнятності плану: "Lock-файл завжди класифікується як
    boilerplate" (без винятків, без перевизначень).
  - **`wiring`** — конфіг-файли (`*.config.*`, `.env*`, `tsconfig*.json`),
    barrel/index-файли (`index.ts`, `index.tsx`), що відповідають власній
    конвенції "translate at the boundary" цього репо для роут-файлів, та
    DI/реєстраційні файли.
  - **`core`** — усе інше (роль за замовчуванням/фолбек — бізнес-логіка це
    "не збіглася з жодним більш специфічним патерном", а не позитивний
    список патернів сама по собі, оскільки бізнес-логіку неможливо вичерпно
    зіставити за шляхом).
  - Порядок зіставлення важливий: патерни boilerplate перевіряються першими
    (найспецифічніші, ніколи не мають бути затінені), потім wiring, інакше
    core.
- Юніт-тестується повністю ізольовано — без `Container`, без БД — це
  природна перша ітерація для TDD.

### 2. Роут: `GET /pulls/:id/smart-diff`

- Новий модуль (або розширення `pulls`, лише якщо прочитання
  onion-architecture імплементером надасть перевагу колокації з `PrDetail` —
  але слід віддавати перевагу невеликому виділеному `modules/smart-diff/` за
  стандартною трифайловою формою, а не подальшому розростанню вже
  нестандартного модуля `pulls`).
- **Вхідні дані** (обидва вже доступні, без жодного нового зовнішнього
  виклику):
  - Рядки `t.prFiles` для PR (`path`/`additions`/`deletions`/`patch` —
    `patch` не потрібен для самої класифікації, лише `additions`/`deletions`
    переходять у `SmartDiffFile.additions`/`deletions`).
  - Findings останнього рев'ю по PR, через новий метод репозиторію, що
    дзеркалить точну форму запиту `pulls/routes.ts:130-157`: рев'ю для цього
    PR, відфільтровані до `kind: 'review'`, `orderBy(desc(createdAt))`,
    береться перший (останній); потім `findings` для цього одного id рев'ю
    через `inArray(t.findings.reviewId, [latestReviewId])`. **Best-effort**:
    якщо жодне рев'ю ще не запускалося, це має деградувати до `[]`, ніколи
    не кидати помилку чи 404-ити всю відповідь Smart Diff (дзеркалить
    прецедент `getIntent(...).catch(() => undefined)` у `pulls/routes.ts:222`).
- **Збірка**: групувати `prFiles` за `classifyFile(path)` у
  `SmartDiffGroup[]`; для кожного файлу встановити `finding_lines` як
  відсортований список значень `start_line` findings цього файлу
  (використовуючи `start_line`, оскільки `Finding` не має єдиного поля
  `line` — `findings.ts:47-73` — уточнити в імплементера, чи достатньо
  самого `start_line`, чи бейдж має покривати весь діапазон
  `start_line`..`end_line`; цей план рекомендує `start_line` як ціль скролу,
  `end_line` — лише якщо UI хоче підсвітити діапазон).
- **`split_suggestion`**: детермінована перевірка порогу, без LLM —
  наприклад `too_big: total_lines > SPLIT_THRESHOLD_LINES` (константа,
  згідно правила "винести пороги" з кроку 1), `total_lines` = сума
  `additions+deletions` усіх файлів, `proposed_splits: []`, якщо не
  включено простий детермінований split-евристику (наприклад, один split на
  кожну не-boilerplate групу) — план домашнього завдання не вимагає
  складного алгоритму розбиття, лише щоб поле було заповнене відповідно до
  наявної форми контракту. Позначити це як рішення про обсяг, яке
  імплементер має явно зазначити, а не мовчки обирати евристику.
- **Відповідь**: `SmartDiff` як уже визначено
  (`server/src/vendor/shared/contracts/brief.ts:93-126`) — зміна контракту
  не потрібна, хіба що семантика `finding_lines` з цього кроку потребуватиме
  додавання severity поряд з кожним рядком (опційне покращення, не вимагається
  критеріями прийнятності в тому вигляді, як вони написані).

### 3. Клієнт: `SmartDiffViewer`

- Нова фіче-папка (дзеркалить форму `IntentCard`:
  `_components/SmartDiffViewer/{SmartDiffViewer.tsx,index.ts,styles.ts}`,
  плюс `constants.ts` для лейблів/кольорів/описів ролей), яку отримують
  через новий хук у `client/src/lib/hooks/reviews.ts` (наприклад
  `useSmartDiff(prId)`, дзеркалить наявні патерни запитів
  `usePrReviews`/`useRefreshIntent`) — звертаючись до `GET /pulls/:id/smart-diff`.
- **Розкладка**, згідно референс-скріншоту домашнього завдання (макет
  `acme/payments-a…`, вкладка "Files changed", перемикач "Smart order" vs
  "Original order" зверху праворуч):
  - Елемент-перемикач (`Smart order` / `Original order`) — smart order
    групує за роллю; original order повертається до звичайного списку
    файлів `DiffTab` (наявна поведінка, без змін) — це задовольняє
    "тримайте boilerplate згорнутим" лише в режимі Smart order і дає шлях
    відступу назад до поточного досвіду.
  - Заголовки груп, по одному на кожну непорожню роль, кожен з коротким
    описом у стилі копірайтингу макету (`Core logic` — "The substance of
    the change — review closely"; `Wiring` — "Hooks the core into the
    app"; `Boilerplate` — "Generated / mechanical — skim") та бейдж
    кількості файлів.
  - Групи `core` та `wiring` **розгорнуті за замовчуванням**; `boilerplate`
    **згорнута за замовчуванням** — це буквальний критерій прийнятності, а
    не стилістична перевага.
  - На файл: бейдж findings (`N findings`, рендериться лише коли
    `finding_lines.length > 0`) — **клікабельний**, скролить diff до файлу
    та підсвічує/переходить до першого (чи вибраного) рядка в
    `finding_lines`. Повторно використати наявні примітиви скролу/підсвітки
    `FileCard`/`CodeLine` з `@/components/diff-viewer`, а не переписувати
    рендеринг diff з нуля — уточнити, який хук скролу-до-рядка вже там існує
    (наприклад, через патерн якір-коментаря `usePrComments`), перш ніж
    писати новий.
- Клієнтський контракт: нові поля не потрібні — `client/src/vendor/shared/contracts/brief.ts`
  вже дзеркалить `SmartDiff` (підтверджено ідентичним цієї сесії).

### 4. Логування / спостережуваність

- Інтеграція `RunLogger`/SSE не потрібна — `GET /pulls/:id/smart-diff` — це
  звичайний HTTP-read, не частина прогону рев'ю, тож він ніколи не
  торкається `server/src/platform/run-logger.ts` чи `RunBus`. Саме так
  природно задовольняється критерій прийнятності "у логах перегляду Smart
  Diff немає нового виклику моделі": контексту прогону рев'ю, в якому міг би
  з'явитися виклик моделі, тут узагалі немає.
- Перевірити (а не просто припустити) через: (a) `grep -n "container.llm(\|resolveFeatureModel("`
  по новому модулю нічого не повертає; (b) жоден новий рядок `agent_runs`
  ніколи не вставляється при зверненні до цього ендпоінта (цю таблицю
  пише лише `run-executor.ts`); (c) вручну звернутися до ендпоінта на
  засіяному PR і підтвердити, що жоден новий pino/stdout рядок, схожий на
  виклик LLM, не з'являється.

## План тестування

- **server-unit** (`cd server && pnpm exec vitest run --exclude '**/*.it.test.ts'`):
  - `classifyFile` — табличні тести: lock-файли → `boilerplate`
    (безумовно, включно з вкладеними шляхами на кшталт
    `packages/foo/package-lock.json`), `dist/`/`__snapshots__/` →
    `boilerplate`, `*.config.*`/`index.ts` → `wiring`, усе інше → `core`.
    Це природна точка входу TDD згідно `superpowers:test-driven-development`.
  - Збірка Smart Diff (мокнутий шар репозиторію, без БД): для фіксованого
    набору `prFiles` + findings, перевірити правильну форму
    `groups`/`finding_lines`/`split_suggestion`; перевірити **нуль
    викликів** будь-якого мокнутого `container.llm`/`resolveFeatureModel`
    (згідно конвенції hermetic-за-замовчуванням із
    `server/src/adapters/mocks.ts`).
- **server-integration** (`cd server && pnpm exec vitest run .it.test`,
  потрібен Docker): новий `*.it.test.ts`, що звертається до
  `GET /pulls/:id/smart-diff` проти реального Postgres — (a) до того, як
  запущено будь-яке рев'ю → всі файли присутні, файли пріоритету `core`
  показують `finding_lines: []`; (b) після рев'ю з findings → правильні
  файли показують непорожні `finding_lines`, що збігаються з `start_line`
  засіяних findings; (c) PR, чиї файли включають lock-файл → цей файл
  щоразу опиняється в групі `boilerplate`.
- **client** (`cd client && pnpm test` + `pnpm typecheck`): тест рендерингу
  для `SmartDiffViewer` — група `boilerplate` починається згорнутою,
  `core`/`wiring` починаються розгорнутими, бейдж findings рендериться лише
  коли `finding_lines` непорожній і є клікабельним, перемикач Smart/Original
  order перемикає вигляди.
- **Ручна smoke-перевірка** (згідно власного розділу "Як перевірити" з
  домашнього завдання, не автоматизується в поточному e2e цього репо
  згідно `TESTING.md`): відкрити великий засіяний PR, підтвердити, що
  `core` показується першим, а lock-файл згорнутий; запустити рев'ю та
  підтвердити, що бейджі з'являються і клік по одному скролить до
  правильного рядка; перевірити серверні логи та підтвердити, що жоден
  новий виклик LLM не спрацював; записати три короткі finding'и у власне
  поле нотаток домашнього завдання.

## Поза межами

- Жоден файл застосунку не створюється й не редагується цим планом самим
  по собі — це лише документ-план, який має виконати імплементер.
- Архітектурний рев'ю та рев'ю безпеки не є частиною цього плану чи
  роботи імплементера — окремі агенти рев'ю відповідають за ці проходи.
- **Складний алгоритм `proposed_splits`** (наприклад, кластеризація файлів
  з урахуванням залежностей) явно поза межами — критерії прийнятності
  вимагають лише, щоб форма контракту `SmartDiff` була заповнена *якоюсь*
  детермінованою, задокументованою евристикою; розумніший splitter — це
  природний наступний крок, тут не вимагається.
- **Заповнення `SmartDiffFile.pseudocode_summary`** поза межами (дивись
  Constraints) — це поле лишається `null`, доки/якщо майбутня ітерація не
  додасть свідомий, окремо визначений крок LLM-сумаризації (якому тоді
  знадобиться власна обробка вартості/логування/prompt-injection, так само
  як Intent Layer).
- **Персистенція результатів Smart Diff** (наприклад, таблиця-кеш
  `smart_diff`) не потрібна — класифікатор дешевий/чистий, а join findings
  — це пара індексованих запитів, тож обчислення при кожному `GET`
  прийнятне; додавати кешування лише якщо профілювання пізніше покаже, що
  це потрібно.
