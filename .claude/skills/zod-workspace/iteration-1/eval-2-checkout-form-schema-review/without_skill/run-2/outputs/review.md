# Code Review: `checkout-form-schema.ts`

Перевірка перед повторним використанням цієї Zod-схеми в новому флоу. Файл: `.claude/skills/zod-workspace/fixtures/checkout-form-schema.ts` (51 рядок).

Загальна оцінка: схема робоча для happy-path, але має один справжній баг у обробці помилок (критично для будь-якого нового споживача) і кілька прогалин у валідації, які легко "успадкувати" в новий флоу непомітно.

---

## Critical

### 1. `refine()` кидає `Error` замість `return false` — ламає контракт `ZodError` (lines 19–24)

```ts
}).refine((data) => {
  if (!data.sameAsShipping && !data.billingAddress) {
    throw new Error('Billing address is required when it differs from shipping');
  }
  return true;
}, { message: 'Billing address is required when it differs from shipping' });
```

**Чому це важливо.** Предикат `refine` має *повертати* `boolean` (або `Promise<boolean>`) — Zod сам перетворює `false` на `ZodIssue` з `code: 'custom'` і зазначеним `message`. Тут замість цього викидається звичайний `Error`. Це означає, що `throw` вилітає з `.parse()`/`.safeParse()` як необроблений виняток ще до того, як Zod встигає його перехопити й обгорнути в `ZodError`.

Наслідок для будь-якого нового флоу, що перевикористовує цю схему: увесь код, який очікує `try { schema.parse(x) } catch (e) { if (e instanceof ZodError) ... }` (стандартний патерн — дістати `e.issues`, змапити на помилки форми), **не спрацює** для цього конкретного випадку невалідності. Помилка або впаде як 500 без структурованого повідомлення, або просто не буде розпізнана як validation error. Другий `message` у другому аргументі `refine` взагалі ніколи не використовується, бо `throw` відбувається раніше, ніж повертається `false`.

**Виправлення:**

```ts
}).refine(
  (data) => !(!data.sameAsShipping && !data.billingAddress),
  { message: 'Billing address is required when it differs from shipping' }
);
```

## High

### 2. `email` не валідується як email (line 12)

```ts
email: z.string(),
```

**Чому це важливо.** Це checkout-форма — email тут використовується як мінімум для отримання квитанції/підтвердження замовлення. `z.string()` пропустить будь-який непорожній рядок ("x", "asdf", навіть порожній рядок, бо `min()` теж не викликано). У новому флоу, куди ви плануєте перенести цю схему, легко забути, що email тут узагалі не перевіряється, і покластися на "раз є Zod-схема — значить формат вже гарантовано валідний".

**Виправлення:**

```ts
email: z.string().trim().min(1).email(),
```

### 3. `refine` не має `path` — помилку неможливо прив'язати до конкретного поля форми (line 24)

```ts
}, { message: 'Billing address is required when it differs from shipping' });
```

**Чому це важливо.** Без `path` issue, який згенерує `refine` (після виправлення п.1), матиме `path: []` — тобто прикріпиться до кореня всього об'єкта, а не до `billingAddress`. Якщо новий флоу підключає цю схему до форми (react-hook-form + `@hookform/resolvers/zod` або аналог), стандартний спосіб показати помилку під конкретним полем — це `errors.billingAddress.message`. З порожнім `path` ця помилка "загубиться" на рівні форми й не відобразиться під потрібним інпутом, або доведеться вручну домальовувати fallback UI для root-помилок.

**Виправлення:**

```ts
}).refine(
  (data) => !(!data.sameAsShipping && !data.billingAddress),
  {
    message: 'Billing address is required when it differs from shipping',
    path: ['billingAddress'],
  }
);
```

### 4. `CheckoutForm` — ручний дублікат типу замість `z.infer` (lines 26–46)

```ts
export interface CheckoutForm {
  email: string;
  fullName: string;
  shippingAddress: { ... };
  ...
}
```

**Чому це важливо.** Тип продубльовано вручну поруч зі схемою, з якої він структурно виведений. Це класичне джерело розсинхронізації: щойно хтось у новому флоу додасть/змінить поле в `CheckoutFormSchema` (наприклад, додасть `phone` або звузить `country` до `z.enum([...])`), інтерфейс `CheckoutForm` мовчки застаріє — TypeScript не підкаже про розбіжність, бо це два незалежні оголошення. Уже зараз тип трохи неточний по формі: `.default(true)` на `sameAsShipping` робить це поле опціональним у *вхідному* (`z.input`) типі, але обов'язковим у *вихідному* (`z.output`) типі — інтерфейс збігається з output лише випадково, бо ніхто це не перевіряє автоматично.

**Виправлення:**

```ts
export type CheckoutForm = z.infer<typeof CheckoutFormSchema>;
```

Якщо вхідний і вихідний тип потрібні окремо (наприклад, для форми до/після застосування `default`), можна експортувати обидва: `z.input<typeof CheckoutFormSchema>` і `z.output<typeof CheckoutFormSchema>`.

## Medium

### 5. `cardLastFour` перевіряє лише довжину, не формат (line 18)

```ts
cardLastFour: z.string().length(4),
```

**Чому це важливо.** `length(4)` пропустить будь-які 4 символи — `"abcd"`, `"12 3"`, емодзі-довжиною-4 і т.д. Для "останніх чотирьох цифр картки" це має бути рівно 4 цифри.

**Виправлення:**

```ts
cardLastFour: z.string().regex(/^\d{4}$/, 'Must be 4 digits'),
```

### 6. `country` перевіряє лише довжину 2, не реальний код країни (line 8)

```ts
country: z.string().length(2),
```

**Чому це важливо.** Пропускає будь-які 2 символи ("XX", "12", "!!"), не лише валідні ISO 3166-1 alpha-2 коди. У новому флоу, якщо цей код піде далі (наприклад, у розрахунок доставки/податків, вибір мови чи інтеграцію зі стороннім API доставки), сміттєве значення тут мовчки пройде валідацію і зламається пізніше, глибше в пайплайні, де діагностувати причину складніше.

**Виправлення:** мінімум — регулярка `/^[A-Z]{2}$/`; краще — `z.enum([...])` зі списком підтримуваних країн, якщо флоу не про весь світ:

```ts
country: z.string().regex(/^[A-Z]{2}$/, 'Must be an ISO 3166-1 alpha-2 code'),
```

### 7. Рядкові поля не тримуються (`.trim()`) — `min(1)` пропускає рядки з самих пробілів (lines 4, 6, 13)

```ts
line1: z.string().min(1),
city: z.string().min(1),
fullName: z.string().min(1).max(120),
```

**Чому це важливо.** `min(1)` перевіряє *довжину* рядка, а не наявність значущого вмісту. Рядок `"   "` (три пробіли) має довжину 3 і пройде `min(1)` без проблем, хоча по суті це порожнє поле. Це поширена помилка, яка призводить до порожніх імен/адрес у БД, що пройшли "валідацію".

**Виправлення:**

```ts
line1: z.string().trim().min(1),
city: z.string().trim().min(1),
fullName: z.string().trim().min(1).max(120),
```

### 8. `line2` та `promoCode` дозволяють порожній рядок `""` як "присутнє" значення (lines 5, 17)

```ts
line2: z.string().optional(),
promoCode: z.string().max(24).optional(),
```

**Чому це важливо.** `.optional()` дозволяє `undefined`, але не забороняє порожній рядок. У формі, яку користувач просто "торкнувся і залишив порожньою", `line2` прийде як `""`, а не `undefined` — і схема це пропустить. Далі в коді доведеться окремо перевіряти `line2 === ''` скрізь, де це поле читається, замість покладатися, що "не задано" == `undefined`/відсутнє.

**Виправлення (варіант із нормалізацією порожнього рядка в `undefined`):**

```ts
line2: z.string().trim().optional().transform((v) => (v === '' ? undefined : v)),
```

## Low / Design notes (варто врахувати саме тому, що схема йде в новий флоу)

- **Немає `.strict()`.** За замовчуванням Zod-об'єкт "тихо" відкидає невідомі ключі (`strip`). Якщо новий флоу пришле поле з опискою в назві (наприклад, `emial` замість `email`), воно мовчки зникне замість помилки. Якщо очікується суворий контракт (наприклад, дані йдуть із форми, яку контролюєте самі), варто розглянути `.strict()` на `CheckoutFormSchema`, щоб хиби в назвах ключів ловилися одразу, а не губилися.
- **`billingAddress` може бути заданий навіть при `sameAsShipping: true`**, і схема це мовчки дозволяє (lines 15–16 + refine перевіряє лише зворотний випадок). Якщо код нижче за течією читає `sameAsShipping` і `billingAddress` окремо, можлива розбіжність даних (наприклад, UI показує "same as shipping", а в БД лежить інша адреса). Варто або ігнорувати/занулювати `billingAddress`, коли `sameAsShipping === true`, через `.transform()`, або явно задокументувати, що поле в такому разі має пріоритет ігнорування на рівні споживача.
- **Постальний код (line 7) не має перевірки набору символів** (`min(3).max(12)` пропускає будь-які символи в межах довжини), аналогічно проблемі з `country` та `cardLastFour` вище — вартувало б хоча б `.trim()`, і за потреби regex, якщо флоу орієнтований на конкретний набір країн з відомими форматами поштових індексів.
- **Пласка структура полів оплати.** `cardLastFour` лежить прямо в корені `CheckoutFormSchema` поруч із адресою і промокодом. Якщо новий флоу передбачає більше одного способу оплати (не тільки картка) або додаткові платіжні поля, зараз немає природного місця для розширення (наприклад, вкладеного `payment: z.discriminatedUnion(...)`). Варто розглянути виокремлення платіжних полів у під-схему вже зараз, перш ніж на неї з'явиться друга точка використання — це дешевше зробити до дублювання, ніж рефакторити пізніше в двох місцях.
- **`validateCheckoutForm` експортує лише `.parse()`-варіант** (кидає виняток). Якщо новий флоу — це, наприклад, API route, що повертає структуровану 400-відповідь замість 500, варто одразу передбачити паралельну `safeParse`-функцію (`validateCheckoutFormSafe`), що повертає `{ success, data | error }`, аби не змушувати кожного нового споживача самостійно обгортати виклик у `try/catch`.

## Підсумок пріоритетів перед перевикористанням

1. Виправити `refine` (throw → return false) — **обов'язково**, інакше обробка помилок у новому флоу буде непередбачуваною.
2. Додати `path: ['billingAddress']` до цього ж `refine`.
3. Додати `.email()` на `email`.
4. Замінити ручний `CheckoutForm` interface на `z.infer<typeof CheckoutFormSchema>`.
5. Інше (regex для `cardLastFour`/`country`, `.trim()` на текстових полях, нормалізація порожніх рядків) — бажано зробити до перенесення в новий флоу, щоб не тягнути ті самі прогалини у ще одне місце коду.
