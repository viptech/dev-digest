## Реконсиляція з наявною імплементацією

**Що ВЖЕ Є і перевикористовується без змін:**

- Таблиці `eval_cases`/`eval_runs` (`server/src/db/schema/eval.ts:7-35`) —
  схема готова, міграції застосовані. Ця спека **не редагує застосовану
  міграцію** — нова колонка (T2 нижче) йде новою міграцією через
  `pnpm db:generate` (root `CLAUDE.md` "Do not touch" — Migrations).

- `EvalsService.run()` (`server/src/modules/evals/service.ts:102-155`) —
  прогін ОДНОГО кейсу проти живого конфігу агента через
  `reviewer-core.reviewPullRequest` (single-pass, без repo-intel) —
  перевикористовується як внутрішній будівельний блок для нового bulk-шляху
  (AC-11), сам ендпоінт `POST /agents/:id/evals/:caseId/run` лишається
  робочим (AC-15).
- `POST /agents/:id/evals`, `PUT/DELETE /agents/:id/evals/:caseId`,
  `GET /agents/:id/evals` (`server/src/modules/evals/routes.ts`) — CRUD
  eval-кейсів, без змін.
- `EvalCaseModal`/`EvalsTab` (`client/.../AgentEditor/_components/EvalsTab/`)
  — ручне створення/редагування кейса, запуск одного кейса, бейдж
  останнього прогону — перевикористовуються, `EvalsTab` РОЗШИРЮЄТЬСЯ (T8),
  `EvalCaseModal` лишається шляхом редагування (в т.ч. кейсів, створених
  кнопкою на `FindingCard` — AC-4).
- `parseGroundingRatio()` (`server/src/modules/evals/helpers.ts:52-58`) —
  парсер `reviewer-core`'ового рядка `"K/N passed"` у 0–1 ratio для
  `citation_accuracy` — перевикористовується буквально, без змін (AC-8).
- Демо-кейси в `seed.ts` (`upsertEvalCase()`,
  `server/src/db/seed.ts:451-488`) — ідемпотентний helper
  перевикористовується, розширюється до ≥8 кейсів (T10).
- Чернетка контрактів `eval-ci.ts` (`server/src/vendor/shared/contracts/eval-ci.ts`)
  — `EvalCaseInput`, `EvalRunRecord`, `EvalRunResult`, `EvalDashboard`,
  `EvalTrendPoint` вже написані, ще ніде не підключені. Ця спека
  ПІДКЛЮЧАЄ `EvalCaseInput`/`EvalRunRecord` (звужуючи `expected_output` до
  типізованого масиву, T1) і `EvalDashboard` (частково — `trend`/`delta`
  на рівні дашборду залишаються неспожитими полями, `Non-goals`), додає
  новий `EvalSetRunResult` (там немає — bulk-прогін не був описаний у
  чернетці).

**Що ЗАМІНЮЄТЬСЯ/розширюється:**

- `ExpectedFinding` (локальний, неекспортований тип у
  `helpers.ts:4-9` — `{severity, file, category?, start_line?}`, без
  поняття "має НЕ знайти") і `matchFindings()`
  (`helpers.ts:25-49` — точний 1:1-збіг множин, `pass` вимагає рівно
  стільки ж `actual`, скільки `expected`) → замінюються типізованим
  `EvalExpectation {type: 'must_find'|'must_not_flag', ...}` і новим
  скорером `scoreEvalCase()` за формулами AC-6/AC-7 (T3). Наявний
  `matchFindings` семантично не розрізняє "агент не повинен був це
  знаходити" від "агент просто знайшов щось зайве" — обидва трактує як
  провал точності однаково; нова формула розрізняє explicit
  `must_not_flag`-порушення (штрафує precision) від знахідки поза
  розміченими зонами (нейтрально, не штрафує — явне рішення, розділ Goals).
- `EvalsService.list()`/`create()` — сьогодні жорстко скоуплені на
  `ownerKind: 'agent'` (`service.ts:43-44`, `57-69`) — це НЕ баг цієї
  спеки; `owner_kind: 'skill'`-кейси схема технічно дозволяє
  (`eval_cases.owner_kind` enum), але жодна UI/route цієї спеки їх не
  обслуговує — залишається так (`Non-goals`).

## Проблема й користувач

**Проблема.** Рецензент (і власник агента) міняє system prompt, модель чи
прилінкований скіл агента "наосліп" — суб'єктивне враження "здається,
краще" чи "здається, галасливіше", без цифр. `eval_cases`/`eval_runs` уже
існують і одиничний прогін кейса вже працює, але немає (а) швидкого шляху
перетворити РЕАЛЬНЕ accept/dismiss-рішення рецензента на регресійний
кейс, (б) прогону ВСЬОГО набору одним кліком з агрегованими цифрами, (в)
історії прогонів і порівняння "було / стало" поруч.

**Користувач.** Власник агента (той самий рецензент, що приймає/відхиляє
знахідки в PR-детальній сторінці — L01–L05), який після зміни промпту
хоче натиснути одну кнопку і побачити: recall не впав, precision не впала,
цитування (`citation_accuracy`) лишилось високим — чи, навпаки, побачити,
що саме зламалось, порівнявши новий прогін зі старим поруч.

## Goals / Non-goals

**Goals**

- Точна схема типізованого очікування, додана до
  `server/src/vendor/shared/contracts/eval-ci.ts` (і синхронно —
  `client/src/vendor/shared/contracts/eval-ci.ts`, за прецедентом
  дублювання без спільного пакета, `root INSIGHTS.md` 2026-07-31):
  ```ts
  export const EvalExpectationType = z.enum(['must_find', 'must_not_flag']);
  export const EvalExpectation = z.object({
    type: EvalExpectationType,
    file: z.string(),
    start_line: z.number().int().nullish(),
    end_line: z.number().int().nullish(),
    severity: Severity.nullish(),
    category: FindingCategory.nullish(),
  });
  ```
  `EvalCaseInput.expected_output` звужується з `z.unknown()` до
  `z.array(EvalExpectation)` (T1) — заміна нетипізованого
  `ExpectedFinding[]`, що сьогодні живе лише як локальний, неекспортований
  TS-інтерфейс у `helpers.ts`.
- **Виправлено 2026-08-19 (див. Open questions) — попередній пункт
  ("одним кліком без модалки, буквально за текстом ДЗ") був хибною
  інтерпретацією.** Підтверджено відеозаписом еталонної реалізації курсу
  (реальний робочий DevDigest, не мокап): клік "Turn into eval case" на
  `FindingCard` (тільки коли `accepted_at`/`dismissed_at` заповнено, AC-2)
  **будує чернетку, НЕ персистує одразу** — відкриває наявний
  `EvalCaseModal` попередньо заповненим: `accepted` → один елемент
  `{type: 'must_find', file: f.file, start_line: f.start_line, end_line:
  f.end_line, severity: f.severity, category: f.category}`, `dismissed` →
  той самий елемент з `type: 'must_not_flag'`; `input_diff` —
  реконструйований single-file unified diff з `pr_files.patch` +
  `pr_files.path` того ж PR (діагностика формату — розділ нижче);
  `owner_id` (для майбутнього persist) — `agent_id` рев'ю, з якого
  знахідка (`ReviewRecord.agent_id`). Персистування відбувається лише
  коли користувач тисне **Save** (чи **Run case**, який зберігає-і-прогонує)
  всередині модалки — тим самим наявним шляхом `useCreateEvalCase`, що вже
  обслуговує ручне створення (AC-4 — кейс і так лишається доступним через
  той самий `EvalCaseModal`, тепер це єдиний шлях персистування, не лише
  редагування).
  Модалка в "seeded"-режимі (за відеозаписом) додатково показує:
  - підпис під заголовком "Seeded from an accepted/dismissed finding —
    assert the expected output";
  - бейдж **POSITIVE CASE**/**NEGATIVE CASE** з людським підсумком
    очікування ("MUST find "<title>" at <file>:<start_line>" /
    "MUST NOT flag ..."), виведений з першого елемента `expected_output`;
  - **Actual output** — повний JSON `run.per_trace[0].actual` після
    прогону (не лише pass/fail-бейдж, який модалка вже показувала);
  - банер статусу прогону з `traces_passed`/`traces_total`/`duration_ms`/
    `cost_usd` (наприклад "0/1 passed · 8.2s · $0.00") — усі ці поля вже
    повертає наявний контракт `EvalRun` (`server/src/vendor/shared/contracts/knowledge.ts:98-107`),
    це рендер наявних даних, не нове поле;
  - кнопка **"Finding skeleton"** — вставляє шаблонний елемент
    `EvalExpectation` в `expected_output`-textarea для ручного дописування;
  - перемикач **"Run on save"** — Save виконує save-and-run замість
    простого save, коли увімкнено;
  - третій таб **"Files"** поруч із наявними Diff/PR meta — список файлів,
    виведений з `diff --git a/... b/...`-заголовків уже наявного
    `input_diff`, без нового джерела даних.
- **Новий** bulk-ендпоінт `POST /agents/:id/eval-runs` (множина — на
  відміну від наявного одиничного `POST
  /agents/:id/evals/:caseId/run`): прогін АГЕНТА на ВСІХ кейсах його
  набору одним викликом, кожен кейс — окремий рядок `eval_runs` (як і
  сьогодні для одиничного прогону) плюс спільний ідентифікатор групи
  прогону (`run_group_id` — нова колонка `eval_runs`, T2; конкретна
  DDL-форма — Development Plan, поведінка "один прогін набору = один
  ідентифікатор групи, N рядків" зафіксована тут).
- Скоринг — повністю кодом, без жодного LLM-виклику всередині самого
  скорера (LLM-виклик — рівно один на кейс, той самий
  `reviewPullRequest`, що вже викликає одиничний прогін; скоринг
  застосовується ПІСЛЯ нього, детерміновано):
  - **Recall** = частка `must_find`-очікувань кейса, для яких є хоча б
    одна повернута знахідка з тим самим `file` і перетином діапазону
    рядків `[start_line, end_line]` (коли очікування не задає
    `start_line`/`end_line` — збіг лише за `file`). Кейс без жодного
    `must_find`-очікування має `recall = 1` (vacuously true — той самий
    "порожньо = 1" принцип, що вже прийнятий наявним `matchFindings`).
  - **Precision** = (кількість повернутих знахідок кейса, що НЕ
    потрапляють у жодну `must_not_flag`-зону) / (загальна кількість
    повернутих знахідок кейса). Знахідка, чиї `file`+діапазон рядків
    перетинаються з `must_not_flag`-зоною, — false positive, НЕ входить у
    чисельник. Знахідка, що не збігається НІ з `must_find`, НІ з
    `must_not_flag` (поза всіма розміченими зонами кейса), —
    **нейтральна: входить у чисельник (не карається)** — явне рішення
    (не єдина можлива альтернатива — див. параграф нижче). Кейс без
    жодної повернутої знахідки має `precision = 1`.
  - **Citation accuracy** — окремо від recall/precision, через
    перевикористаний `parseGroundingRatio(outcome.grounding)` — частка
    знахідок кейса, що пережили grounding-гейт `reviewer-core`. НІКОЛИ не
    змішується з precision/recall в один показник (Non-goals; AC-24).

  **Явно відхилена альтернатива для "знахідки поза розміченими зонами".**
  Розглядався варіант карати precision за будь-яку знахідку поза
  анотованими зонами (трактувати "не в `must_find` і не в
  `must_not_flag`" як автоматичний false positive) — відхилено: це
  вимагало б повної розмітки КОЖНОГО рядка diff'а кожного кейса, щоб
  precision взагалі мав сенс, а курс (`03-key-concepts.md`) свідомо
  обмежує учнівський pipeline точковою розміткою (кілька `must_find`/
  `must_not_flag`-зон на кейс, не вичерпний перелік). Нейтральна
  трактовка — узгоджена з цим духом; якщо власник продукту вирішить
  інакше, це localized зміна однієї формули в `scoreEvalCase()`
  (`server/src/modules/evals/helpers.ts`), не архітектурна.
- Історія прогонів набору й порівняння двох поруч: кожен `eval_runs`-рядок
  зберігається назавжди (жодного UPSERT/перезапису — на відміну від
  `pr_brief` у SPEC-04), список set-run'ів агента групується за
  `run_group_id`; порівняльний вигляд показує дельту (новий − старий) по
  кожній з трьох метрик і по кожному кейсу окремо (pass→fail / fail→pass),
  НЕ лише агреговані числа (AC-18–AC-19).
- Окрема сторінка "Eval Dashboard" у лівому сайдбарі (`client/src/vendor/ui/nav.ts`,
  новий пункт у секції `SKILLS LAB`, за прецедентом наявних `skills`/
  `conventions`/`agents`) — список агентів з їхнім останнім set-run'ом.
- Явна відмова від єдиного непрозорого score: recall/precision/
  citation_accuracy/cost_usd/duration_ms завжди рендеряться як окремі,
  незалежні значення (AC-24) — анти-паттерн уроку, якого спека свідомо
  уникає.
- Явна відмова від висновку "агент покращився/зламався" з ОДНОГО прогону:
  UI не показує жодного "regression"/"improved"-індикатора, доки не
  обрано рівно два прогони для порівняння (AC-25) — другий анти-паттерн
  уроку.

**Відоме, свідомо прийняте обмеження скорера (не ховається).** Матчер
порівнює лише `file` + перетин діапазонів рядків — не розуміє семантику
змісту. Наслідки:
- Дві РІЗНІ проблеми, заявлені на тому самому рядку (напр. одночасно і
  SQL-injection, і забутий `console.log`), скорер порахує як ОДИН збіг
  (перше зайняте `expected`-очікування "з'їдає" будь-яку знахідку на
  тому самому рядку).
- Та сама проблема, що модель знайшла на зсунутому рядку (напр. після
  рефакторингу коду вище у файлі), скорер НЕ визнає збігом — recall
  впаде хибно, хоча агент фактично знайшов проблему.

Це прийнятне навчальне обмеження цього курсу (`03-key-concepts.md`
буквально описує той самий компроміс) — фіксується тут явно, не
приховується як деталь реалізації.

- **`PreToolUse`-хук, що автоматично блокує зміну промпту/коду без
  зеленого eval-прогону** — поза обсягом; evals цієї спеки
  запускаються вручну кнопкою, не автоматично на кожен edit.
- **Mutation testing самих eval-кейсів** (навмисне псування коду для
  перевірки, чи кейс взагалі здатен щось зловити) — поза обсягом; курс
  лише вимагає одного контрольованого експерименту "зіпсований промпт →
  precision падає" (T12), не систематичної мутаційної перевірки набору.
- **Перевірка якості самих accept/dismiss-рішень як ground truth** —
  кнопка "Turn into eval case" довіряє рішенню рецензента без додаткової
  ручної верифікації; якщо рецензент помилково прийняв хибну знахідку,
  кейс успадковує цю помилку без detection. Той самий анти-паттерн уроку
  ("вважати accept/dismiss без ручної перевірки безпомилковими labels")
  — тут явно НЕ вирішується, лише документується як відоме обмеження
  (Edge cases).
- Кешування/дедуплікація однакових set-run'ів — кожен явний клік "Run
  all" завжди виконує повний прогін (той самий "явна кнопка = завжди
  свіжий виклик" принцип, що вже прийнятий `PrBriefCard`'s Regenerate,
  SPEC-04).
- Видалення окремого set-run'у з історії — не специфіковано текстом ДЗ;
  рекомендація в Open questions, не блокер AC.

## User stories

- Як власник агента, я відкриваю PR, бачу знахідку, яку рецензент щойно
  прийняв (`accepted_at` заповнено) — тисну "Turn into eval case" на
  картці, кейс `{type: must_find, file, start_line, end_line, severity,
  category}` одразу з'являється в наборі агента без жодної проміжної
  форми.
- Як той самий власник, я бачу поруч знахідку, яку рецензент щойно
  відхилив (`dismissed_at` заповнено) — тисну ту саму кнопку, отримую
  кейс `{type: must_not_flag, ...}` — регресійний захист "більше не
  галасуй про це".
- Як власник агента, я відкриваю вкладку Evals в `AgentEditor`, бачу
  набір із ≥8 кейсів (мікс `must_find`/`must_not_flag`), тисну "Run all"
  — за один клік прогоняю весь набір, бачу агреговані recall/precision/
  citation_accuracy й список per-case результатів.
- Як той самий власник, я міняю system prompt агента, тисну "Run all"
  ще раз, відкриваю історію прогонів, обираю старий і новий прогін —
  бачу дельту по кожній метриці й список кейсів, що змінили pass/fail
  між прогонами.
- Як той самий власник, я навмисно псую промпт (прибираю інструкцію
  ловити critical-проблеми) — прогоняю набір ще раз — бачу, що precision
  видимо впала, не читаючи жодного окремого прогону вручну.
- Як людина, що переглядає стан усіх агентів, я відкриваю нову сторінку
  Eval Dashboard у лівому сайдбарі — бачу список агентів з останнім
  set-run'ом кожного, без заходу в кожен `AgentEditor` окремо.

## Acceptance criteria (EARS)

**Створення кейса зі знахідки**

- **AC-1** (event-driven) — **виправлено 2026-08-19, див. Open questions**.
  КОЛИ рецензент натискає "Turn into eval case" на `FindingCard` для
  знахідки з заповненим `accepted_at` АБО `dismissed_at`, система (shall)
  побудувати чернетку eval-кейса БЕЗ запису в БД: `owner_kind: 'agent'`,
  `owner_id` = `agent_id` рев'ю цієї знахідки, `expected_output` = масив з
  одним `EvalExpectation` (`type: 'must_find'` для `accepted`, `type:
  'must_not_flag'` для `dismissed`; `file`/`start_line`/`end_line`/
  `severity`/`category` — з самої знахідки), `input_diff` —
  реконструйований single-file unified diff для `f.file` (нижче) — і
  (shall) відкрити цю чернетку в наявному `EvalCaseModal` для перегляду/
  редагування; сам запис `eval_cases` (shall) створюватись лише коли
  користувач тисне Save/Run case в модалці (той самий шлях, що AC-4).
- **AC-2** (unwanted behavior). ЯКЩО знахідка не має ні `accepted_at`, ні
  `dismissed_at` (рішення ще не прийнято), ТО кнопка "Turn into eval
  case" (shall) бути неактивною — жодного кейса без прийнятого рішення.
- **AC-3** (unwanted behavior). ЯКЩО рев'ю знахідки не має `agent_id`
  (напр. `summary`-рев'ю без прив'язаного агента), ТО система (shall)
  відмовити створенню кейса з цієї знахідки (кнопка неактивна на клієнті
  АБО сервер повертає 422 "Finding's review has no agent") — eval-кейс
  без власника-агента існувати не може.
- **AC-4** (ubiquitous) — **розширено 2026-08-19**. Чернетка з AC-1
  (shall) відкриватись і персистуватись через той самий наявний
  `EvalCaseModal` (`POST`/`PUT /agents/:id/evals[/:caseId]`), що вже
  створює/редагує кейси вручну — жодного окремого, паралельного шляху
  персистування чи редагування для кейсів, народжених зі знахідки.

**Типізовані очікування й скоринг**

- **AC-5** (ubiquitous). `expected_output` кожного eval-кейса (shall)
  бути масивом `EvalExpectation {type: 'must_find'|'must_not_flag', file,
  start_line?, end_line?, severity?, category?}` — валідованим цією
  схемою на вході (`POST`/`PUT /agents/:id/evals...`), заміна
  нетипізованого `unknown`.
- **AC-6** (ubiquitous). Recall кейса (shall) дорівнювати частці
  `must_find`-очікувань, для яких є ≥1 повернута знахідка з тим самим
  `file` і перетином діапазону рядків `[start_line, end_line]`
  (очікування без `start_line`/`end_line` збігається за самим `file`);
  кейс без жодного `must_find`-очікування (shall) мати `recall = 1`.
- **AC-7** (ubiquitous). Precision кейса (shall) дорівнювати відношенню
  (кількість повернутих знахідок, чиї `file`+рядки НЕ перетинаються з
  жодною `must_not_flag`-зоною) до (загальна кількість повернутих
  знахідок); знахідка поза всіма розміченими зонами кейса (shall)
  вважатись нейтральною й входити в чисельник (не каратись); кейс без
  жодної повернутої знахідки (shall) мати `precision = 1`.
- **AC-8** (ubiquitous). `citation_accuracy` кейса (shall) обчислюватись
  через `parseGroundingRatio(outcome.grounding)` — незалежно від
  recall/precision, той самий, уже наявний механізм.
- **AC-9** (ubiquitous). Система (shall) виконувати ввесь скоринг (AC-6–
  AC-8) кодом, без жодного LLM-виклику всередині самого скорера — рівно
  один LLM-виклик на кейс (`reviewPullRequest`, той самий, що одиничний
  прогін уже робить), скоринг застосовується ПІСЛЯ нього.
- **AC-10** (unwanted behavior). ЯКЩО той самий діапазон рядків одного
  кейса позначено одночасно і в `must_find`, і в `must_not_flag`
  (суперечливе розмічення), ТО система (shall) враховувати перетин з
  обома зонами незалежно (внесок і в recall-чисельник, і в
  precision-штраф одночасно) — без валідаційної заборони такого кейса на
  запис (аномальний, але не блокований край).

**Bulk-прогін набору**

- **AC-11** (event-driven). КОЛИ клієнт викликає `POST
  /agents/:id/eval-runs`, система (shall) прогнати живий конфіг агента
  (system_prompt/model/увімкнені лінковані скіли — той самий resolution,
  що одиничний прогін) на КОЖНОМУ кейсі набору (`owner_kind: 'agent',
  owner_id: :id`), персистуючи для кожного кейса окремий рядок
  `eval_runs` (як і одиничний прогін), і (shall) проставити тим рядкам
  спільний `run_group_id`.
- **AC-12** (event-driven). КОЛИ bulk-прогін (AC-11) завершується,
  система (shall) повернути: `run_group_id`, агреговані
  recall/precision/citation_accuracy набору (просте середнє по кейсах —
  macro-average, кожен кейс важить однаково незалежно від кількості його
  очікувань чи знайдених findings) і список per-case результатів
  (`case_id`, `case_name`, `pass`, `recall`, `precision`,
  `citation_accuracy`, `cost_usd`, `duration_ms`).
- **AC-13** (unwanted behavior). ЯКЩО набір кейсів агента порожній, ТО
  `POST /agents/:id/eval-runs` (shall) повернути 422 без жодного
  LLM-виклику.
- **AC-14** (unwanted behavior). ЯКЩО прогін ОКРЕМОГО кейса всередині
  bulk-прогону падає (мережева помилка LLM, невалідна відповідь), ТО
  система (shall) позначити цей кейс `pass: false` з `recall`/
  `precision`/`citation_accuracy: null` у per-case результаті, НЕ
  перериваючи прогін решти кейсів набору.
- **AC-15** (ubiquitous). Наявний одиничний `POST
  /agents/:id/evals/:caseId/run` (shall) лишатись робочим і незмінним
  поруч із новим bulk-ендпоінтом — не видаляється, не замінюється AC-11.

**Історія прогонів і порівняння**

- **AC-16** (ubiquitous). Система (shall) зберігати кожен bulk-прогін
  (AC-11) як нові рядки `eval_runs` — без UPSERT/перезапису попередніх
  (на відміну від `pr_brief` у SPEC-04) — кожен прогін лишається окремим
  для історії й порівняння.
- **AC-17** (event-driven). КОЛИ рецензент відкриває вкладку Evals в
  `AgentEditor`, система (shall) показати список історичних set-run'ів
  агента, згрупованих за `run_group_id`, найновіший перший, з
  агрегованими метриками кожного (AC-12).
- **AC-18** (event-driven). КОЛИ рецензент обирає рівно два set-run'и зі
  списку історії для порівняння, система (shall) відрендерити їх поруч:
  recall/precision/citation_accuracy кожного і дельту (новий − старий)
  для кожної з трьох метрик окремо, з візуальним індикатором напрямку
  (зростання/спад).
- **AC-19** (ubiquitous). UI-порівняння (AC-18) (shall) також показувати
  per-case розбіжності — які кейси перейшли `pass → fail` чи `fail →
  pass` між двома обраними прогонами, не лише агреговані числа.

**Eval Dashboard**

- **AC-20** (event-driven). КОЛИ користувач відкриває нову сторінку Eval
  Dashboard з лівого сайдбару, система (shall) показати список агентів
  воркспейсу з їхнім останнім set-run'ом (агреговані
  recall/precision/citation_accuracy, час прогону, кількість кейсів у
  наборі) — той самий агрегат, що AC-12, без per-case деталізації
  (перехід у деталі — вкладка Evals конкретного агента).
- **AC-21** (state-driven). ПОКИ агент ще не мав жодного set-run'у,
  відповідний рядок Eval Dashboard (shall) показувати порожній стан
  ("Never run") без падіння сторінки й без запиту, що падає з помилкою.

**Захист від cost-abuse**

- **AC-22** (unwanted behavior). ЯКЩО `POST /agents/:id/eval-runs`
  викликається частіше, ніж дозволяє ліміт `{max: 5, timeWindow: '1
  minute'}` (нижчий за одиничний прогін — bulk фан-аутить до N
  LLM-викликів, N = розмір набору), ТО система (shall) відхилити
  перевищуючий запит (429).

**Доступ і прозорість**

- **AC-23** (unwanted behavior). ЯКЩО `:id` агента (`POST
  /agents/:id/eval-runs`) чи знахідка (`POST /findings/:id/eval-case`,
  AC-1) не належить воркспейсу викликача, ТО система (shall) повернути
  404 ДО будь-якого LLM-виклику чи запису в БД.
- **AC-24** (unwanted behavior). ЯКЩО UI рендерить метрики прогону
  (одиничного чи set-run'у), ТО recall/precision/citation_accuracy/
  cost_usd/duration_ms (shall) відображатись як окремі, незалежні
  значення — система (shall) НЕ обчислювати і НЕ показувати єдиний
  "зведений score", що змішує ці виміри.
- **AC-25** (unwanted behavior). ЯКЩО показано лише ОДИН set-run (немає
  другого обраного для порівняння), ТО UI (shall) НЕ рендерити жодного
  "regression"/"improved"-індикатора — такий індикатор з'являється
  виключно в порівняльному вигляді (AC-18) при явно обраних двох
  прогонах.

## Edge cases

- Знахідка без `accepted_at`/`dismissed_at` → кнопка неактивна (AC-2), не
  прихована повністю (рецензент бачить, що дія доступна лише після
  рішення).
- Рев'ю без `agent_id` (summary-рев'ю) → AC-3, кейс не створюється.
- Дві знахідки з тим самим `file`+перетином рядків, різні `severity`
  (наприклад одна `CRITICAL`, одна `WARNING`) → кожна утворює свій
  окремий `EvalExpectation`, якщо обидві перетворено на кейси окремо —
  скорер (AC-6/7) розглядає їх як два незалежні очікування того самого
  кейса, якщо вони опинилися в одному кейсі вручну; типовий шлях (AC-1)
  створює по одному кейсу на знахідку, тож колізії немає за замовчуванням.
- Суперечливе розмічення (той самий рядок і в `must_find`, і в
  `must_not_flag`) — AC-10, явно не заблоковано, `scoreEvalCase()` рахує
  внесок в обидва боки.
- `pr_files.patch` для файлу знахідки порожній/`null` (GitHub іноді не
  повертає patch для дуже великих чи бінарних файлів) → реконструкція
  диффа (AC-1) не може зібрати валідний unified diff — кейс усе одно
  створюється, але з порожнім `input_diff`; майбутній прогін такого
  кейса поводиться так само, як наявний `EvalsService.run()`'s guard на
  порожній `inputDiff` (`ValidationError`, `service.ts:110-112`) —
  перевикористаний контракт помилки, не новий.
- Набір агента порожній на момент `POST /agents/:id/eval-runs` → AC-13.
- LLM недоступний під час прогону ОДНОГО кейса з N у наборі → AC-14,
  решта кейсів набору все одно прогоняються.
- Два set-run'и обрані для порівняння належать РІЗНИМ агентам (не мають
  бути технічно порівнювані — кожен `run_group_id` прив'язаний до
  конкретного набору кейсів конкретного агента) → UI обмежує вибір
  порівняння лише прогонами ТОГО САМОГО агента (список історії, AC-17,
  вже відфільтрований по `:id` з роуту).
- Агент, чий набір кейсів змінився МІЖ двома порівнюваними прогонами
  (кейс додано чи видалено після старого прогону) → порівняння per-case
  (AC-19) показує кейс, відсутній в одному з двох прогонів, як "no data"
  для цього прогону, не як `fail` — не вигадана хибна регресія.
- Матчер зіставляє лише файл+рядки, не семантику (описано в Goals як
  явне обмеження) — конкретний прояв: рефакторинг, що зсуває рядки без
  зміни логіки, псує recall наявних кейсів навіть якщо агент поведінково
  не деградував; це очікувана крихкість навчального pipeline, не баг.
- Ground truth (сам факт accept/dismiss) міг бути помилковим рішенням
  рецензента (Non-goals) — кейс, створений з хибного рішення,
  успадковує цю помилку без детекції.
- Порівняння показує лише ОДИН прогін (історія agента ще не має другого)
  → AC-25, ніякого regression/improved індикатора, лише список одного
  прогону.

## Non-functional requirements

Пропущено через скіл `security` (OWASP Top 10:2025 / Agentic AI Security
ASI01/ASI09) — той самий обсяг перевірки, що вже застосований у SPEC-01/
SPEC-03/SPEC-04 до їхніх LLM-викликів і недовіреного контенту. Знахідки:

- **MEDIUM — cost abuse через bulk-прогін (A06 Insecure Design).**
  `POST /agents/:id/eval-runs` фан-аутить до N LLM-викликів за один HTTP
  запит (N = розмір набору кейсів) — суттєво дорожче за одиничний
  прогін. Мітигація — тісніший rate-limit `{max: 5, timeWindow: '1
  minute'}` (AC-22), нижчий за прецедент `{max: 10, ...}` одиничних
  генерацій (SPEC-04's `/pulls/:id/brief`, `/pulls/:id/review`).
  **Супутня знахідка, не частина обсягу цієї спеки:** наявний одиничний
  `POST /agents/:id/evals/:caseId/run`
  (`server/src/modules/evals/routes.ts:73-82`) СЬОГОДНІ не має жодного
  rate-limit'у — той самий клас cost-abuse, що вже існує до цієї спеки.
  Рекомендація — задати той самий бекфіл окремим, мінімальним фіксом
  (не в обсязі SPEC-05; див. Open questions).
- **HIGH → MEDIUM (за наявним контролем) — доступ до чужого workspace
  (A01 Broken Access Control).** Нові ендпоінти (`POST
  /agents/:id/eval-runs`, `POST /findings/:id/eval-case`) (shall)
  перевіряти належність `:id`/знахідки воркспейсу викликача ДО
  будь-якого запису в БД чи LLM-виклику (AC-23) — той самий,
  вже наявний паттерн (`getContext` + `workspaceId`-фільтр у кожному
  наявному роуті цього модуля, `evalsRoutes`, `EvalsService.update/
  delete`'s `ownerId !== agentId` перевірка, `service.ts:78`, `92`).
- **LOW — довіра до LLM-виходу, що стає ground truth (ASI09 Trust
  Exploitation).** `expected_output`, створений кнопкою (AC-1), похідний
  від FINDING, який сам є LLM-виходом попереднього прогону, лише
  проведеним через людське accept/dismiss-рішення. Це НЕ новий канал
  ін'єкції (значення, що йдуть у `EvalExpectation` — структуровані
  `file`/`start_line`/`end_line`/`severity`/`category`, ніколи прозовий
  `rationale`/`title` знахідки не копіюється в поле, що пізніше йде в
  ЩЕ ОДИН LLM-промпт) — але точність нового кейса лише настільки хороша,
  наскільки хорошим було саме рішення рецензента (задокументовано як
  Non-goal, не мітигується технічно).
- **LOW — injection через `input_diff`, що йде в новий LLM-виклик
  (ASI01 Goal Hijacking).** `input_diff`, реконструйований для нового
  кейса (AC-1), — той самий реальний PR-diff, який `reviewPullRequest`
  вже обробляв раніше через `reviewer-core`'ів `wrapUntrusted()`/

  паралельного шляху конкатенації diff'а в промпт без існуючого
  injection guard'а не додається.
- **LOW — логування.** Структурований лог кожного (bulk чи одиничного)
  прогону (shall) нести лише `caseId`/`agentId`/`runId`/
  `run_group_id`/резолвлену модель/`recall`/`precision`/

  `CLAUDE.md`.
- **Прозорість вимірів (не безпекова, але явна вимога курсу).**
  recall/precision/citation_accuracy/cost/latency НІКОЛИ не згортаються
  в один непрозорий score (AC-24) — анти-паттерн уроку, зафіксований як
  hard-вимога, не рекомендація.

## Inputs and provenance

- **Знахідка → eval-кейс** — `FindingRecord` (уже персистований, з
  `accepted_at`/`dismissed_at`) + батьківський `ReviewRecord.agent_id` —
  жодного нового джерела даних, лише нова похідна від наявних таблиць
  (`findings`, `reviews`).
- **`input_diff` кейса, створеного кнопкою** — реконструйований з
  `pr_files.patch` + `pr_files.path` (`server/src/db/schema/pulls.ts:36-45`)
  того PR, до якого належить рев'ю знахідки; `parseUnifiedDiff()`
  (`server/src/adapters/git/diff-parser.ts:14-60`) очікує повний
  `diff --git a/<path> b/<path>` + `--- a/<path>` + `+++ b/<path>` +
  `@@ ... @@`-заголовок ПЕРЕД тілом хунка — GitHub API повертає в
  `patch`-полі лише саме тіло хунка (без `diff --git`/`+++`/`---`
  рядків), тож сервіс (shall) синтезувати ці три заголовкові рядки з
  `pr_files.path` перед тим, як передати результат у `parseUnifiedDiff`
  всередині майбутнього прогону.
- **Bulk-прогін (`actual_output`)** — живий виклик `reviewPullRequest`
  (`@devdigest/reviewer-core`), той самий resolution живого конфігу
  агента, що вже застосовує одиничний `EvalsService.run()`.
- **`citation_accuracy`** — `outcome.grounding` (рядок `"K/N passed"` від
  `reviewer-core`'ового grounding-гейта, root `CLAUDE.md`'s "grounding
  gate ... never bypassed") через перевикористаний `parseGroundingRatio()`.
- **Персистовані set-run'и** — нові рядки `eval_runs`, що діляться
  спільним `run_group_id` (нова колонка, T2); історія й порівняння
  читають виключно ці персистовані рядки, без окремого кешу.
- **Eval Dashboard** — агрегат обчислюється на льоту з `eval_runs`,
  фільтрований по `owner_id` кожного агента воркспейсу; без окремої
  кеш-таблиці в обсязі цієї спеки.

## Untrusted inputs

- **`input_diff` кейса (як створеного вручну, так і кнопкою)** — реальний
  вміст PR-diff, той самий клас недовіри, що вже проходить через
  `reviewPullRequest`'s наявний `wrapUntrusted()`/`INJECTION_GUARD`
  всередині `reviewer-core` при кожному прогоні (одиничному чи bulk) —
  ця спека НЕ вводить нового шляху конкатенації diff'а в промпт повз цей
  механізм.
- **`FindingRecord.file`/`start_line`/`end_line`/`severity`/`category`**
  — використовуються кнопкою (AC-1) лише як СТРУКТУРОВАНІ значення
  (копіюються в типізовані поля `EvalExpectation`), ніколи не
  конкатенуються в жодний текстовий промпт-фрагмент — джерело недовіри
  те саме (LLM-вихід попереднього прогону), але шлях використання
  вужчий за прозовий текст.
- **`actual_output` (знахідки з bulk/одиничного прогону)** — вихід LLM,
  персистується як є (той самий контракт, що наявний `EvalsService.run()`
  вже персистує); НІКОЛИ не логується прозовим текстом (NFR), рендериться
  в UI лише як структуровані поля (file/line/severity/category), не через
  `dangerouslySetInnerHTML`.
