# engineering-insights — специфікація скіла

**Дата:** 2026-07-28
**Статус:** затверджено, до реалізації
**Джерело досліджень:** `L01/engineering-insights-research.md`

## Задача

Після кодової задачі агент записує практичні знахідки сесії — неочевидні
залежності, підтверджені фікси, виміряні факти, контрінтуїтивні знахідки — у
`INSIGHTS.md` того модуля, якого торкалась робота. Кожен запис має доказ
`file:line` і дату.

Проблема, яку це вирішує: агент живе в межах context window. Після завершення
сесії не персиститься нічого — наступна сесія повторює ті самі помилки і
перевідкриває ті самі квірки. `INSIGHTS.md` — це нотатки, які попередня версія
агента залишила для наступної.

## Що це НЕ

- **Не заміна документації.** README і CLAUDE.md описують, як система працює.
  INSIGHTS фіксує те, що з'ясувалося на практиці і чого з коду не видно.
- **Не реплей чату.** Записується витяг знання, а не історія дій.
- **Не git log.** «Додав ендпоінт X» — не інсайт. Це вже є в історії комітів.

## Архітектура

### Розташування скіла

`.claude/skills/engineering-insights/SKILL.md`

Це **перший локально написаний скіл** у репозиторії. Решта десять
(`zod`, `security`, `fastify-best-practices`, …) — вендорені з GitHub і
відстежуються в `skills-lock.json` із полями `source` + `computedHash`. Наш скіл
у lock-файл **не** додається: він не має апстріму, і запис із фейковим джерелом
зламав би перевірку цілісності.

Наявні скіли — довідкові (знання про бібліотеку). Цей — процесний (workflow).
У каталог `.claude/skills/README.md` додається рядок із явною позначкою типу.

### Цільові файли

П'ять можливих `INSIGHTS.md`, за фактичною структурою репозиторію:

| Робота торкалась | Файл |
|---|---|
| `client/**` | `client/INSIGHTS.md` |
| `server/**` (включно з `repo-intel` — він усередині сервера) | `server/INSIGHTS.md` |
| `reviewer-core/**` | `reviewer-core/INSIGHTS.md` |
| `e2e/**` | `e2e/INSIGHTS.md` |
| кілька модулів одразу, `server/src/vendor/shared`, `scripts/`, CI, Docker | `INSIGHTS.md` у корені |

> **Виправлення щодо дослідження.** Добірка оперує шляхами `apps/client`,
> `apps/server`, `packages/reviewer-core`, `packages/repo-intel`. У цьому
> репозиторії такої структури немає: пакети лежать у корені без префіксів, а
> `repo-intel` — не окремий пакет, а модуль сервера
> (`server/src/modules/repo-intel`). Мапінг вище — за реальним деревом.

### Визначення модуля

Модуль визначає **модель за контекстом сесії** — які файли читались і
редагувались.

*Свідомий компроміс.* Дослідження двічі зазначає, що детектор кодом надійніший за
судження моделі (`git diff --name-only` → мапінг за префіксом). Обрано простіший
варіант: скіл лишається чистим markdown без виконуваних команд. Ціна — на довгих
сесіях модуль можуть визначити неточно або звалити все в кореневий файл. Це
природний кандидат на посилення в пізнішому уроці.

### Тригер

Подвійний:

1. **Wrap-up** — у кінці кодової задачі.
2. **Capture as you go** — щойно натрапив на неочевидне, не чекаючи кінця.

Кеденс: задачі, де було розбирання проблеми, ухвалене рішення або відкриття.
Тривіальні правки пропускаються.

**Свідомо без хука.** Скіл не спрацьовує сам — його викликають, або агент вирішує,
що він доречний. Це відомий недолік: «if you skip the wrap-up, the system doesn't
learn». Для L01 це навмисно: студент бачить і ефект накопичення, і ненадійність
ручного тригера. L06 замикає це Stop-хуком, який робить capture безвідмовним.

## Формат

Плоский хронологічний **append-only** лог. Дописування завжди в кінець файлу —
агенту важко помилитися, порожніх секцій не виникає, чистка за датою тривіальна.

> Розглядався варіант із сімома фіксованими секціями (What Works / What Doesn't
> Work / Codebase Patterns / Tool Notes / Recurring Errors / Session Notes / Open
> Questions). Відхилено: на п'ять файлів це дає багато напівпорожнього каркасу, а
> вставка в середину файлу помилковіша за дозапис у кінець.

### Структура запису

```markdown
## YYYY-MM-DD · <категорія>
**<Твердження одним рядком>**
<Чому це важливо / що з цим робити.>
Доказ: <шлях:рядок>
```

Приклад:

```markdown
## 2026-07-28 · gotcha
**Інтеграційні тести самі себе скіпають без Docker**
Зелений прогон ≠ вони виконались — перевіряй, що контейнер справді піднявся.
Доказ: server/test/helpers/pg.ts:14
```

### Категорії

| Категорія | Що фіксує |
|---|---|
| `dependency` | неочевидний зв'язок: зміна тут ламає щось там |
| `fix` | підтверджений фікс: симптом → причина → що допомогло |
| `measured` | виміряний факт: число, час, ліміт, поріг |
| `gotcha` | контрінтуїтивна поведінка інструмента чи коду |
| `decision` | ухвалене рішення разом із причиною |

### Мова

Інструкції скіла — англійською (як решта документації репозиторію і як усі інші
`SKILL.md`). Самі записи в `INSIGHTS.md` — українською, мовою команди.

## Планка якості

**Тест на банальність:** якби це було очевидно будь-кому, хто читає код — не пиши.

**Доказ `file:line` обов'язковий** і виконує роль фільтра: якщо знахідку нема чим
підперти, це, найпевніше, здогадка, а не інсайт.

Vague vs useful:

| Погано | Добре |
|---|---|
| «З промісами буває складно» | «`Promise.all()` на пайплайні інжесту таймаутить після 30 елементів — бери `Promise.allSettled()` батчами по 10» |
| «Обережно з async» | «State checkout-флоу завжди через Zustand (`cartStore.ts`), бо кошик шарять 3 компоненти» |

Не писати: перефразування коментарів із коду; переказ того, що зроблено; загальні
поради з підручника; здогадки без перевірки.

## Контроль розростання

- **Append-only.** Старий запис ніколи не переписується. Якщо він виявився хибним
  або застарів — додається новий датований запис, що це спростовує, з посиланням
  на попередній.
- **Орієнтир ~200 записів** на файл. Далі сигнал/шум падає — потрібна чистка
  застарілого або дроблення на доменні файли.
- **INSIGHTS — чернетка під спот-чек.** Модель може хибно підсумувати; записи
  періодично переглядає людина.
- Файли комітяться в git — знання шариться з командою.

## Замикання петлі (CLAUDE.md)

Без читання на старті файл перетворюється на мертвий архів. У `CLAUDE.md`
додається секція з двома правилами:

1. **Перед роботою** — прочитати `INSIGHTS.md` відповідного модуля (і кореневий)
   і трактувати як high-confidence guidance, доки не сказано інше.
2. **У кінці кодової задачі** — викликати `engineering-insights` і дописати
   знахідки.

## Обсяг реалізації

Три файли:

1. `.claude/skills/engineering-insights/SKILL.md` — новий
2. `.claude/skills/README.md` — рядок у каталозі + позначка локального скіла
3. `CLAUDE.md` — секція замикання петлі

Самі `INSIGHTS.md` не створюються порожніми — перший запис створює файл. Порожній
каркас лише додав би шум у п'яти місцях.

## Критерії успіху

- Виклик скіла після кодової задачі дає щонайменше один запис із валідним
  `file:line`, який вказує на реально існуючий рядок.
- Запис проходить тест на банальність — його не можна отримати, просто прочитавши
  README.
- Скіл не створює запису, коли задача була тривіальною.
- Нова сесія, прочитавши `INSIGHTS.md`, не перевідкриває зафіксовану квірку.
